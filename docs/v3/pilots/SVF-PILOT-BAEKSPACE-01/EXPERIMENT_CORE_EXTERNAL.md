# SVF-PILOT-BAEKSPACE-01 — EXPERIMENT_CORE_EXTERNAL

**Experiment ID:** BAEK-CORE-E1  
**As-of:** 2026-09-19  
**Status:** READY FOR EXTERNAL DISCOVERY — NOT YET RUN  
**Primary hypotheses:** H1, H3  
**Related option:** A

---

## 1. Question

> **Do external users with a real AI/Markdown document job voluntarily use the current BaekSpace Core more than once, and what blocks that repeated job?**

This experiment is not a general usability test.

It is designed to discriminate:

- H1 Core-first value;
- H3 expansion-inertia.

---

## 2. What must remain unchanged during E1

Do not add strategic features merely to improve the experiment result.

Allowed before participant use:

- critical bug/security fixes;
- completion of already-required human G7 checks;
- copy/instructions needed to make the existing product understandable.

Not allowed:

- building Organize/Publish/graph features to satisfy speculative requests;
- adding Studio workflow;
- changing the North Star mid-test.

If a blocker appears, record it first. Do not immediately code it.

---

## 3. Participant entry

Use the pre-solution screen from `MEASUREMENT_CONTRACT.md`.

Prefer Core-fit participants who already:

- save/reopen AI output;
- work with Markdown/text;
- or have a concrete local/privacy need.

Do not recruit generic “tech curious” users merely because they will try a tool.

---

## 4. Session structure

### Phase 1 — Current workflow, no product

Ask:

- Show me what happens after an AI gives you something worth keeping.
- Where does it go?
- What do you reopen later?
- What is hard to find again?
- What do you edit?
- What material would you avoid uploading to another service?
- What tool would you normally use for today's document?

Record the substitute before showing BaekSpace.

### Phase 2 — Give one job, not a tour

Instruction:

> **Use BaekSpace with one real document you actually care about. Treat it as your own workspace.**

Do not demonstrate every feature.

Observe:

- first action;
- navigation confusion;
- whether they use reader/editor/library;
- whether Zero-Upload matters spontaneously;
- whether they ask for something before completing the job.

### Phase 3 — Leave with the product

Ask them to use it during the next week **only if a real need appears**.

Do not instruct:

> “Please come back three times.”

The experiment wants voluntary return.

A short reminder may be sent only for the follow-up interview, not to manufacture product usage.

---

## 5. Observations

Capture:

- target job;
- substitute;
- time to first meaningful action;
- task completed?;
- facilitator intervention?;
- feature discovered naturally?;
- blocker?;
- requested feature;
- did request block job or merely improve it?;
- voluntary return?;
- second job;
- document revisited?;
- what would they use if BaekSpace disappeared tomorrow?

---

## 6. Core experiment signposts

### A-STRONG

Potentially strengthens Option A / Core investment when the Measurement Contract's promising signal is met and repeat use is tied to a coherent job.

### A-NARROW

If repeat use appears only in a specific segment/job:

> narrow the product promise before expanding.

### C-BLOCKER

If at least two independent users hit the same repeated-job blocker:

> authorize investigation of that specific missing capability.

This is not a blanket authorization for Option C.

### A-WEAK

If users complete the demo but do not voluntarily return:

> H1 weakens.

Do not respond by adding random features.

Investigate:
- wrong segment;
- weak job;
- switching friction;
- product explanation;
- insufficient differentiation.

---

## 7. Evidence that would surprise us

Record explicitly if:

- users ignore reading and mainly use editing;
- privacy is never mentioned;
- ASCII/structured rendering never matters;
- users use BaekSpace as a temporary viewer but refuse the library;
- users return primarily because of a capability not considered central.

Surprise is more valuable than confirmation.

---

## 8. Output

Return one structured record per participant plus:

- repeated-job pattern;
- common blocker pattern;
- substitute pattern;
- hypotheses strengthened/weakened;
- whether C gained any legitimate feature authorization;
- commercial evidence level change, if any.

No overall “satisfaction score” is required.
