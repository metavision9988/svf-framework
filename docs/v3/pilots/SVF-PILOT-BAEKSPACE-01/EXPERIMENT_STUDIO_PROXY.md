# SVF-PILOT-BAEKSPACE-01 — EXPERIMENT_STUDIO_PROXY

**Experiment ID:** BAEK-STUDIO-P1  
**As-of:** 2026-09-19  
**Status:** READY AS MANUAL/DISPOSABLE PROXY — NO STUDIO BUILD AUTHORIZED  
**Primary hypotheses:** H2, H4, H5, H6, H7  
**Related options:** B, D

---

## 1. Question

> **Does the Studio job create repeated behavior before Studio software exists?**

The experiment deliberately separates:

> **job validation**

from

> **software validation**.

If the job is weak, building S0–S2 will not rescue it.

---

## 2. No-code / disposable rule

Do not create a production `baekspace-studio` repo for this experiment.

Allowed forms:

- Markdown worksheet;
- simple local HTML mock;
- spreadsheet/table;
- paper/card workflow;
- facilitator-maintained prototype.

The proxy must be cheap enough to throw away.

The purpose is to test:

- Projects;
- Topics;
- Today;
- Next Action;
- return/update behavior.

Not visual polish.

---

## 3. Problem interview first

Before revealing Studio, ask:

- What unfinished work is currently open?
- Where are those ideas/projects stored?
- How do you choose what to work on today?
- When do you lose context?
- How often do you plan instead of finish?
- What gets abandoned?
- What do you do when you have too many possible next actions?
- What tool/process do you already use?

H2 is stronger only when the pain appears **before solution exposure**.

---

## 4. Minimal proxy model

Use only four objects:

### Project
A meaningful outcome that may take multiple actions.

### Topic
A smaller thread/question inside a project.

### Next Action
The smallest concrete action that moves the work.

### Today
A deliberately small view of what can be acted on now.

No additional taxonomy in P1.

---

## 5. Today rule

To avoid facilitator intuition masquerading as product intelligence, use a simple declared rule.

Candidate order:

1. explicit deadline within 7 days;
2. otherwise participant-marked priority;
3. otherwise the oldest active item with a valid Next Action.

Surface no more than **3 candidates**.

Participant chooses one.

If the participant overrides the rule, record the reason.

This rule is a disposable test mechanism, not the future Studio algorithm.

---

## 6. First session

Participant:

1. enters 1–3 real Projects;
2. creates only Topics necessary for current work;
3. writes one Next Action per active Project;
4. sees Today candidates;
5. chooses one action;
6. performs or schedules that real-world action.

Measure setup burden.

If setup itself feels like “more project management,” record it as core evidence against H2.

---

## 7. Seven-day use

The proxy is available for 7 days.

Observe whether the participant voluntarily:

- completes the action;
- updates it;
- chooses a new action;
- reopens a Project;
- records a new idea;
- removes/stops an irrelevant item.

Do not praise maintenance for its own sake.

The desired behavior is **progress**, not database hygiene.

---

## 8. Studio signposts

### B-JOB-STRONG

H2 strengthens when:

- the pain was independently present before concept exposure;
- users complete real Next Actions;
- repeated return occurs without facilitation;
- participants say what existing substitute failed, with concrete examples.

This can authorize a **small software implementation decision**, not a full Studio roadmap.

### H5-OWNER-BIAS

H5 strengthens when:

- participants do not recognize the pain;
- structure feels tailored to the owner's workflow;
- Projects/Topics are too elaborate;
- users already have sufficient substitutes.

### H7-ONE-PRODUCT

H7 strengthens when:

- users repeatedly expect the Studio workflow inside current BaekSpace;
- product separation is confusing;
- the job is tightly tied to documents already living in Core.

### H4-SPLIT

H4 strengthens when:

- users clearly distinguish “document home” from “progress workflow”;
- the same person can explain when they would use each;
- combining them feels cognitively crowded.

---

## 9. Build authorization rule

### Studio S0–S2 is **not** authorized merely because:

- users like the mock;
- owner finds it useful;
- participants ask when it will launch.

A first build becomes reasonable only when the Measurement Contract's Studio promising signal is met **and** the main friction appears to be missing software rather than lack of job value.

Then the authorized scope is only:

- S0 skeleton;
- S1 import/entry;
- S2 Today/Next Action.

No roadmap pull-forward.

---

## 10. Stop / narrow rule

Do not build Studio if the proxy shows:

- structure abandonment;
- no voluntary return;
- no behavior change;
- a clearly sufficient current substitute;
- pain limited to the owner or an extremely narrow non-commercial case.

Possible output is:

> keep the workflow as an internal personal method.

That is a valid result.

---

## 11. Output

Per participant:

- pre-existing pain;
- current substitute;
- project/topic setup;
- Today choice;
- Next Action;
- action completion;
- voluntary return;
- maintenance burden;
- split-vs-one-product expectation;
- willingness to continue;
- new unknowns.

No software code is required to complete P1.
