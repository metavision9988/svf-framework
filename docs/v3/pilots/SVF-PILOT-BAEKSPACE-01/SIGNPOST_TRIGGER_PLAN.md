# SVF-PILOT-BAEKSPACE-01 — SIGNPOST_TRIGGER_PLAN

**Pilot ID:** SVF-PILOT-BAEKSPACE-01  
**As-of:** 2026-09-19  
**Status:** PRECOMMITTED BEFORE EXTERNAL RESULTS

---

## 1. Purpose

This document answers:

> **What evidence would actually change the plan?**

A signpost is an observed condition.

A trigger is the predeclared decision response.

These are pilot governance rules, not universal product laws.

---

## 2. Current decision options

- **A** — validate / continue investing in current Core
- **B** — authorize Studio S0–S2
- **C** — implement a specific missing Core blocker
- **D** — continue dual validation before larger build
- **N** — narrow segment/job
- **HOLD** — insufficient evidence
- **STOP** — stop a hypothesis/product path

---

## 3. Signposts

### S1 — Core voluntary return

Observed:

Core-fit users independently return and perform a real repeated job.

**Trigger:**
- strengthen H1;
- continue A;
- identify the recurring job;
- do not expand feature scope unless S3 also occurs.

---

### S2 — Core no-return

Observed:

participants complete first use but do not return naturally.

**Trigger:**
- weaken H1;
- HOLD broad Core expansion;
- investigate segment/job/substitute before coding.

Do not “fix retention” by adding many features without blocker evidence.

---

### S3 — Repeated Core blocker

Observed:

at least two independent Core-fit users hit the same missing capability and cannot complete/repeat the target job.

**Trigger:**
- open a bounded Option C investigation;
- define exact capability and acceptance criterion;
- implement only after confirming cheaper workaround is inadequate.

---

### S4 — Studio pain exists before solution

Observed:

multiple Studio-fit users independently describe the overload/completion pain before seeing Studio.

**Trigger:**
- strengthen H2;
- continue Studio proxy;
- weaken H5 owner-bias.

---

### S5 — Studio behavior change

Observed:

participants perform real Next Actions and voluntarily return to update/choose another.

**Trigger:**
- strengthen H2/H6;
- if Measurement Contract promising signal is met, permit a decision on B S0–S2.

Not yet permission for a full roadmap.

---

### S6 — Studio structure abandonment

Observed:

participants stop maintaining the proxy or describe it as additional administrative work.

**Trigger:**
- weaken H2;
- strengthen H5;
- simplify objects before any build;
- if persistent after simplification, STOP or keep as internal method.

---

### S7 — Core and Studio both show signal

Observed:

both jobs produce repeated behavior, potentially in different segments.

**Trigger:**
- continue D;
- segment users/jobs;
- do not force a single winner;
- test product relationship and handoff.

This may imply two products, one suite, or one core plus workflow layer. Evidence decides later.

---

### S8 — Core strong, Studio weak

**Trigger:**
- choose A / narrow Core positioning;
- HOLD B;
- preserve Studio docs as deferred hypothesis;
- no Studio repo.

---

### S9 — Core weak, Studio strong

**Trigger:**
- consider B S0–S2;
- stop adding Core features except those required as reusable infrastructure;
- reassess whether BaekSpace becomes infrastructure/reader layer rather than flagship.

---

### S10 — Both weak

**Trigger:**
- STOP expansion;
- return to problem/segment discovery;
- do not rescue either path with additional engineering.

---

### S11 — Product split confusion

Observed:

users cannot explain why Core and Studio are separate or expect one surface.

**Trigger:**
- strengthen H7;
- test one-product IA or shared shell;
- do not commit branding/architecture split yet.

---

### S12 — Product split clarity

Observed:

users clearly explain different jobs and transition points.

**Trigger:**
- strengthen H4;
- separate-product architecture remains plausible.

---

## 4. Commercial signposts

### CS1 — External problem confirmation

Target users independently describe the same pain and substitute.

**Possible evidence movement:** M0 → M2 candidate.

### CS2 — Behavioral commitment

External participant gives real material, returns, schedules follow-up, or brings a colleague.

**Possible evidence movement:** toward M3 candidate.

### CS3 — Paid commitment

Not part of this internal round.

A future paid workshop/pilot may support M4.

Do not ask hypothetical pricing and label it M4.

## 5. Decision table

| Core signal | Studio signal | Default next direction |
|---|---|---|
| strong | weak | A / N |
| weak | strong | B S0–S2 consideration |
| strong | strong | D + segment/product relationship test |
| weak | weak | HOLD / STOP / problem discovery |
| ambiguous | ambiguous | extend discovery; no build |
| strong + repeated blocker | any | bounded C for blocker only |

“Strong” means the precommitted pilot signal in `MEASUREMENT_CONTRACT.md`, not subjective enthusiasm.

---

## 6. Review points

Required review events:

1. after first 3 meaningful external sessions — **diagnostic only**, no strategic winner;
2. after minimum viable Core/Studio-fit evidence is collected;
3. after 7-day follow-up window;
4. before authorizing any Studio code or major Core feature.

Early evidence may stop a harmful experiment, but should not declare market victory.

---

## 7. Anti-hindsight rule

If a trigger seems wrong after results appear:

- execute the interpretation under the original trigger first;
- then record a versioned critique;
- do not silently change the trigger and claim it was always the rule.

That critique becomes SVF methodology evidence.
